# PROD KICKS: SUPABASE AUTHENTICATION, STAFF APPROVAL & RBAC SYSTEM

Implement the complete authentication, staff approval, role, and permission system for the existing Prod Kicks application.

The frontend already exists.

We're using the supabase cloud for authentication and database

Do not redesign the application. Integrate this system into the existing frontend and follow the existing project's component patterns, styling, routing, and architecture.

Security must be enforced by Supabase/PostgreSQL. Hiding buttons or routes in React is only for UX and must never be treated as authorization.

---

# CORE REQUIREMENTS

Prod Kicks does NOT have normal customer/member accounts.

Authentication exists exclusively for employees/staff.

Users authenticate through Discord.

A newly authenticated Discord user must NOT automatically receive staff access.

The lifecycle is:

Discord OAuth
→ Profile Setup
→ Pending Approval
→ Approved + Assigned Role
→ Employee Portal Access

Users who authenticate but never complete profile setup should NOT appear in the approval queue.

---

# ACCOUNT STATES

Support the following account states:

- NULL = profile setup has not been completed
- pending = profile submitted and awaiting approval
- approved = approved employee
- declined = request was declined
- disabled = previously approved employee whose access has been revoked

Do not give pending, declined, disabled, or incomplete accounts access to protected employee functionality.

---

# ROLES

Create these roles:

- developer
- owner
- manager
- staff

Use a PostgreSQL enum if appropriate.

## Developer

Developer is a special super-admin role.

Developer:

- Automatically has every permission.
- Does NOT depend on role_permissions.
- Cannot be assigned through the application.
- Can only be assigned manually through the database/Supabase dashboard.
- Cannot have their role changed through the application.
- Cannot be disabled through the application.
- Cannot be deleted through the application.
- Should never appear as an option in any role assignment dropdown.

Developer can:

- Approve Staff
- Approve Manager
- Approve Owner
- Change non-developer roles
- Configure permissions for Owner, Manager and Staff
- Perform every protected application action

Do not create a frontend mechanism that can grant Developer.

---

# ROLE HIERARCHY

Role hierarchy and feature permissions are separate concepts.

Role hierarchy controls which roles someone may assign.

Implement this hierarchy:

Developer:
- Can assign Owner
- Can assign Manager
- Can assign Staff

Owner:
- Can assign Manager
- Can assign Staff

Manager:
- Can assign Staff

Staff:
- Cannot assign roles

Nobody can assign Developer through the application.

Enforce this hierarchy server-side/database-side.

Do not rely only on filtering dropdown options in React.

# PROFILE SUBMISSION

Do NOT allow arbitrary direct client updates to sensitive fields in `staff_accounts`.

Create a secure PostgreSQL function/RPC such as:

`submit_staff_profile(full_name, state_id)`

It must use the currently authenticated `auth.uid()`.

Do not accept a user UUID from the browser for this operation.

The function should:

1. Confirm the caller is authenticated.
2. Confirm their staff account exists.
3. Confirm they are allowed to complete profile setup.
4. Validate Full Name.
5. Validate State ID.
6. Confirm State ID is not already assigned to another account.
7. Save Full Name.
8. Save State ID.
9. Set `profile_completed_at = now()`.
10. Set `status = 'pending'`.
11. Keep `role = NULL`.
12. Update `updated_at`.

Do not allow profile submission to assign a role.

After successful submission:

→ redirect to `/`

They should now appear in the approval queue.

# SECURITY REQUIREMENTS

Treat all browser input as untrusted.

Never expose the Supabase service role key in frontend code.

Frontend may only use the public Supabase client configuration.

Sensitive administrative operations must happen through secure PostgreSQL functions/RPCs, RLS, or a secure server environment if genuinely required.

Never trust:

- role supplied by frontend
- account status supplied by frontend
- permission list supplied by frontend
- user UUID supplied as the acting user
- hidden buttons
- protected React routes

Use `auth.uid()` to establish the acting user wherever possible.

Prevent privilege escalation.

A Staff user manually calling Supabase APIs must not be able to:

- approve themselves
- change their role
- change their status
- grant permissions
- assign Developer
- modify another employee
- access unauthorized tables
- modify draft/private data without permission

A Manager must not be able to promote someone to Manager or Owner.

An Owner must not be able to promote someone to Owner.

Nobody using the application may assign Developer.

---

# IMPORTANT TABLE SECURITY

Users should not have general UPDATE access to `staff_accounts`.

Separate ordinary profile actions from administrative actions using RPCs.

A user should never be able to send something like:

```ts
supabase
  .from("staff_accounts")
  .update({
    role: "developer",
    status: "approved"
  })
  .eq("id", user.id)
```

and have it succeed.

RLS must reject this.
